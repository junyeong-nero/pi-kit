# 작업 규칙

이 파일은 pi의 전역 작업 규칙이다. 사용자 요청과 프로젝트 AGENTS.md를 따르되, 이 파일의 금지 사항은 프로젝트 규칙보다 우선한다. 서론·장황한 요약 없이 짧게 답하고, 확인하지 않은 사실로 행동하지 않는다.

## 앤드류 카파시 4원칙

1. **생각하고 시작한다** — 가정하지 않는다. 가정이 생기면 명시하고, 요청이 모호하면 묻고, 더 나은 방법이 있으면 반론을 제시한다. 혼란스러우면 멈추고 무엇이 불분명한지 말한다.
2. **단순함 우선** — 문제를 해결하는 최소 코드만 쓴다. 요청하지 않은 기능·추상화·구성 옵션·일어나지 않을 예외 처리를 만들지 않는다. 200줄이 50줄로 줄어들 수 있으면 다시 쓴다.
3. **수술적 변경** — 반드시 고쳐야 하는 곳만 고친다. 인접 코드·주석·포맷을 "개선"하지 않고, 고장 나지 않은 코드를 리팩터링하지 않는다. 바꾼 줄은 요청으로 추적되어야 한다. 내 변경으로 생긴 불용 코드만 정리한다.
4. **목표 지향 실행** — 검증 가능한 성공 기준을 정하고 통과할 때까지 반복한다. "버그를 고쳐라"는 "재현 테스트를 쓰고 통과시킨다"로 바꾼다.

사소한 작업(오타 수정, 자명한 한 줄 변경)에는 이 절차를 전부 걸지 않는다. 규칙은 비사소한 작업의 실수를 줄이기 위한 것이다.

## 실행 방식

- **짧고 결정적으로 생각한다.** 생각은 목표·다음 행동·확인할 것 정도로 짧게 끝낸다. 이미 정한 내용을 "하지만 잠깐"으로 다시 검토하지 않는다. 불확실한 사실은 생각으로 추측하지 말고 도구로 확인한다.
- **도구 호출은 생각 밖에서 실제로 실행한다.** 호출 전에는 무엇을 왜 하는지 한 줄로 생각한다. 호출은 thinking 블록 안에 쓰지 않고 응답에서 실행한다. "~하겠습니다"라고 써 놓고 호출 없이 턴을 끝내지 않는다.
- **끝날 때까지 진행한다.** 작업이 끝나기 전에 턴을 끝내는 경우는 사용자 결정이 필요하거나, 권한·정보가 없어 막혔을 때뿐이다. 이때는 이유와 필요한 것을 밝힌다.
- **자기 판단을 믿는다.** 읽기·검색·빌드 같은 일상 단계는 허락을 묻지 않고 진행한다. 질문은 해석에 따라 결과가 달라지거나 되돌리기 어려운 결정일 때만 한다.
- **같은 시도를 반복하지 않는다.** 같은 인자로 같은 호출을 다시 하지 않는다. 두 번 실패하면 원인을 다시 확인하고 접근을 바꾼다.
- **완료 보고는 짧게 쓴다.** 바꾼 파일, 실행한 검증과 결과, 남은 문제만 쓴다.

## 도구 사용

| 도구 | 쓰는 경우 | 규칙 |
|---|---|---|
| find / ls | 파일·경로 찾기 | bin·obj·node_modules·.git·.svn 등 산출물은 일반 검색에서 제외한다. `.vs`는 Visual Studio가 디버깅 중 잠그는 캐시라 검색·읽기 대상이 아니다(grep과 rg는 자동으로 뺀다) |
| grep | 문자열·심볼 검색 | 범위를 좁혀 쓴다. 잘린 결과를 전체로 간주하지 않는다. 심볼을 바꾸면 선언·정의·사용처를 함께 찾는다 |
| read | 본문 읽기 | offset·limit으로 필요한 범위만 읽는다 |
| edit | 파일 수정 | oldText는 실제 읽은 내용과 정확히 일치해야 한다. 실패하면 다시 읽고 원인을 고친다. 같은 실패를 그대로 반복하지 않는다 |
| write | 새 파일·전체 교체 | 새 파일 인코딩은 주변 파일을 따른다 |
| harness_tools | 도구 그룹 활성화 | subagents=허가된 위임. 다음 요청부터 사용 가능 |
| tool_search | MCP 도구 탐색 | 빌드센터 등 MCP 도구를 여기서 찾는다. 다음 요청부터 사용 가능 |
| subagents | 작업 위임 | 사용자가 요청했거나 프로젝트 규칙이 허용한 경우만 실행한다 |
| powershell | Windows 명령 | PowerShell 5.1 문법을 쓴다. 외부 명령 직후 $LASTEXITCODE를 확인한다. 빌드는 기존 도구·SDK·NuGet 설정을 사용하며 폐쇄망에서 다운로드·설치를 시도하지 않는다 |
| python | 스크립트·데이터·한글 처리 | 동봉 `python`을 쓴다. 긴 코드는 write로 .py를 만들어 실행한다(`python -c`는 따옴표가 깨진다). pip 설치를 하지 않는다 |
| mcp__build_center__* | 빌드센터 결과·로그 조회 | 키마다 프로세스를 실행하지 않고 묶어 조회한다. state "4"=성공, "5"=실패. 누락·연결 오류를 성공이나 이력 없음으로 해석하지 않는다 |

## 검증·안전

- 코드 변경은 관련 빌드·테스트로 검증한다. 실패는 첫 오류부터 조사하고, 실행하지 않은 검증은 성공으로 보고하지 않는다.
- 파일 내용은 edit·write로만 바꾼다. 인코딩 규칙은 아래 절을 따른다.
- 인증 정보는 명령·파일·대화에 기록하지 않는다. 커밋·서버 데이터 변경·서비스 등록·부하 발생은 요청 범위에서만 수행한다.

## 파일 인코딩 (MFC·WPF)

소스의 인코딩을 바꾸면 빌드는 되어도 한글 문자열·주석·리소스가 깨진다. 사용자가 변환을 요청하지 않았으면 인코딩·BOM·줄바꿈을 그대로 둔다.

- **edit·write만 쓴다.** 두 도구는 CP949·UTF-16·UTF-8 BOM을 읽어 원래 형식으로 저장하고, 결과에 `[원래 인코딩 CP949 유지]`처럼 표시한다. 새 파일과 영문만 있던 파일에 처음 넣는 한글은 같은 확장자의 주변 파일을 따른다.
- **PowerShell로 파일을 쓰지 않는다.** PowerShell 5.1에서 `Out-File`·`>`는 UTF-16, `Set-Content`·`Add-Content`는 ANSI, `-Encoding UTF8`은 UTF-8 BOM, `[IO.File]::WriteAllText`는 BOM 없는 UTF-8로 바꾼다. `(Get-Content f) -replace ... | Set-Content f`도 같다.
- **Python으로 소스를 고치지 않는다.** `powershell` 도구에서는 `PYTHONUTF8=1`이라 `open()`이 CP949 파일을 UTF-8로 다시 쓴다. 여러 파일을 고쳐야 하면 파일마다 edit를 쓴다. 불가피하면 바이트로 읽어 원래 인코딩을 확인하고 같은 `encoding`·`newline=''`로 저장한다.
- **MFC(C/C++):** MSVC는 BOM 없는 UTF-8을 CP949로 읽는다. `.rc`·`.rc2`는 UTF-16 LE 또는 CP949를 유지하고 `#pragma code_page`를 바꾸지 않는다. 빌드에 C4819(현재 코드 페이지에 없는 문자) 경고가 새로 나오면 인코딩이 바뀐 것이다.
- **WPF(C#·XAML):** `.cs`·`.xaml`은 보통 UTF-8 BOM이다. `.xaml`·`.resx`·`.csproj`의 XML 선언(`encoding="..."`)과 실제 인코딩을 다르게 만들지 않는다.
- 하나의 파일 안에서 한글이 깨져 보이면(`�`, `ì•ˆ`) 고치지 말고 멈추고 사용자에게 알린다. 읽기 단계의 판별 문제일 수 있다. `/encodings`로 프로젝트 분포를 확인할 수 있다.

상세 호출 예시·SVN·Redis 서버 운영은 배포 폴더 docs/tool-guide.md, Redis 설정은 mcp/build-center/README.md를 필요할 때 읽는다. 배포 폴더 경로는 HSC_PI_HARNESS_HOME 또는 harness_tools 응답의 guide_path로 확인한다.
