# 폐쇄망 코딩 에이전트 — 발표자 노트

자료: [setup-slides.html](setup-slides.html). 본문 18장 + 설치·근거 부록 4장. 권장 발표 시간 15–20분, 부록은 질의에 따라 사용한다.

설명 원칙: 대상 환경의 설계 조건과 실제 조직 전체의 조사 결과를 혼동하지 않는다. 모델/제품 간 우위를 주장하지 않는다. 로컬 통합 테스트와 사내 업무 성과를 구분한다.

## 1. 폐쇄망에서 코드 수정과 검증을 연결하기

설치법을 소개하기 전에 왜 이 구성이 필요한지부터 설명한다. 핵심은 모델의 답변을 실제 프로젝트에서 수정하고 확인하는 업무로 연결하는 것이다.

## 2. 핵심 질문: AI가 고친 코드를 어떻게 확인할까?

오늘 발표는 문제, 설계, 검증의 순서로 진행한다. 가설은 언어 분석 피드백을 편집 직후 돌려주면 오류를 더 일찍 확인할 수 있다는 것이다. 시간 단축 효과는 아직 측정 전이며 구현 가능성과 업무 효과를 구분한다.

## 3. 도입 조건은 모델 연결보다 넓다

이 슬라이드는 현재 저장소가 대상으로 삼은 운영 조건이다. 회사 전체의 실측 조사 결과로 소개하지 않는다. 폐쇄망이라는 말은 모델까지 완전히 네트워크 없이 실행한다는 뜻이 아니다. 사내 모델 API와 로컬 분석 서버의 경계를 구분한다.

## 4. 대화·검색·빌드만으로는 피드백이 끊긴다

각 접근은 유효한 기능을 제공한다. 문제는 그 결과가 에이전트의 반복 작업으로 자동 연결되는지다. 기존 사내 시스템이 모두 이와 같다는 단정이나 특정 제품의 불가능 판정은 피한다. 전체 빌드와 테스트는 제안 구조에서도 반드시 남는다.

## 5. 업무 제약을 네 가지 설계 기준으로 바꾼다

요구사항마다 확인 가능한 기준을 붙인다. 이런 기준을 먼저 정해야 특정 도구를 골랐다는 설명보다 설계 선택의 근거가 분명해진다. 실행기 준비와 프로젝트 빌드 환경 준비는 서로 다른 검증 대상이다.

## 6. Harness는 모델이 일하는 실행 환경이다

이 발표에서 harness는 모델 주변의 실행 환경이라는 뜻으로 사용한다. 모델 자체를 새로 학습하는 작업은 아니다. pi는 대화 상태와 도구 실행 흐름을 제공하고, 이 저장소는 그 위에 배포 구성과 LSP 연결을 더한다.

## 7. 왜 pi를 기반으로 구성했는가?

선택 이유는 모델 성능 우위가 아니라 이 저장소의 구성 가능성이다. 자체 에이전트를 만들면 실행 루프와 세션 관리까지 구현해야 하고, IDE 중심 접근은 설치 환경과 연동 범위를 별도로 설계해야 한다. pi를 선택하면서 절약한 부분과 계속 책임져야 하는 통합 검증을 함께 설명한다.

## 8. 사내 추론과 로컬 분석을 하나의 작업 흐름으로

상단은 모델 서비스이고 하단은 개발 PC다. 언어 서버는 로컬 별도 프로세스로 실행된다. 다만 로컬 분석이라는 사실이 코드나 진단이 모델 API로 전달되지 않는다는 뜻은 아니다. 에이전트가 구성한 코드 맥락과 도구 결과는 사내 모델에 전달될 수 있다.

## 9. LSP: 언어 분석 기능을 호출하는 공통 규약

LSP는 분석 알고리즘이나 LLM이 아니라 통신 규약이다. 프로토콜을 이해하는 클라이언트가 언어 서버에 요청한다. 따라서 서버마다 제공하는 기능과 분석 범위가 다르고, 올바른 빌드 맥락도 필요하다.

## 10. 같은 문자열과 같은 심볼은 다르다

문자열 검색은 넓게 후보를 찾는 데 유용하다. 그다음 정확한 위치에서 어느 선언에 연결되는지 묻는 역할을 LSP가 맡는다. 이 예시는 개념 설명이며 모든 동적 호출이나 전처리 상황을 완벽하게 해석한다는 뜻은 아니다.

## 11. 편집 직후 진단을 다음 행동으로 돌려준다

연결되는 지점은 pi의 편집 결과 이벤트다. LSP는 필요할 때 탐색 도구로도 호출한다. 오류를 전달하면 모델이 수정할 수 있지만 자동으로 모든 문제가 해결된다는 보장은 없다. 최종 완료 판단에는 빌드, 테스트, 사람의 검토가 필요하다.

## 12. 분석의 품질은 프로젝트 맥락에 달려 있다

언어 서버 실행 파일을 가져온 것만으로 모든 프로젝트가 분석되지는 않는다. C++에서는 빌드에 쓰는 플래그와 헤더를 전달해야 한다. C#에서는 대상 SDK와 패키지가 준비돼야 한다. 현재 자동으로 모든 vcxproj를 변환하는 기능은 없다.

## 13. 세 확장이 서로 다른 역할을 맡는다

핵심 검증 흐름은 cpp-csharp-lsp-lite가 맡고 lens는 보조 분석, subagents는 작업 분담을 맡는다. lens의 LSP를 끈 이유는 서버와 진단 경로 중복을 피하기 위해서다. 확장을 늘리면 모델 호출 비용과 상호 간 호환성 확인도 늘어난다.

## 14. 설치 절차를 재현 가능한 오프라인 묶음으로

생성기는 필요한 파일을 고정 버전으로 준비하고, 배포 대상 PC에는 npm이나 Python의 별도 설치가 필요 없다. Redis MCP용 Python과 패키지도 ZIP에 동봉한다. 대상 PC에서는 setup.ps1을 한 번 실행해 시스템 Path와 설정 폴더(`PI_CODING_AGENT_DIR` = `config\`)를 등록하고, 이후 어느 폴더에서나 `pi`로 실행한다. 로그인 때 사용자 환경 변수를 초기화하는 PC가 있어 사용자 변수 대신 시스템 변수를 쓴다. 비밀 값과 세션은 표준 ZIP에 넣지 않는다.

## 15. 동작 확인과 업무 효과 입증을 구분한다

테스트 결과는 이번 작업에서 실제로 확인한 범위만 말한다. 단위 테스트는 LSP 7개와 패키징 4개다. 모델 응답은 결정론적 로컬 fixture이므로 실제 사내 모델의 계획 능력이나 작업 품질을 입증하지 않는다. 새 확장 조합(97b5071)의 Windows CI도 성공했다. ZIP 재배치, 서버 외부 통신 차단 검증, standalone pi 도구 호출까지 통과했다. 백그라운드 자식 실행 전체를 검증한 것은 아니다.

## 16. 다음 실험은 “LSP가 실제로 도움이 되는가”

이 슬라이드는 완료된 실험이 아니라 평가 제안이다. 우선 LSP만 켜고 끄는 비교로 효과를 분리한다. lens나 subagents까지 동시에 추가하면 무엇이 기여했는지 알기 어렵다. 실행 순서를 섞고 과제별로 반복하며 실패 사례도 함께 기록한다.

## 17. 운영 도입 전에 확인할 네 가지

남은 과제를 구현 실패처럼 다루지 않고 어떤 조건에서 도입 여부를 판단할지 설명한다. 실제 프로젝트에서 수집할 데이터가 다음 단계다. 외부 통신을 줄이는 설정은 조직의 네트워크 통제 자체를 대체하지 않는다는 점도 필요하면 덧붙인다.

## 18. 도입은 대표 프로젝트의 작은 과제부터

핵심 메시지를 운영 순서로 정리한다. 하나의 대표 프로젝트와 범위가 작은 수정 작업으로 시작해 연결 상태와 완료 기준을 먼저 확인한다. 질문이 설치로 넘어가면 부록으로 이동한다.

## 19. 현재 구성: setup.ps1로 한 번 설정하고 pi로 실행

GitHub Actions가 검증해 Release에 올린 완성 ZIP 하나를 반입한다. GitHub 소스 ZIP이나 CI Artifact는 쓰지 않는다. setup.ps1(scripts/setup.ps1)는 pi를 실행하지 않고 한 번만 설정한다. 필수 파일을 확인하고, 시스템 Path에 `bin`·`bin\pi`·ast-grep 폴더를 넣고, `PI_CODING_AGENT_DIR`을 `config\`로 지정한다. `-Check`는 아무것도 바꾸지 않고 파일 존재 여부만 확인한다. models.json, settings.json, 전역 AGENTS.md 등 pi 설정은 모두 `config\` 한 곳에 있다.

## 20. 압축 해제 → 사내 모델 설정 → setup.ps1 → pi

API 키는 예시 값이다. 사용자 환경 변수는 로그인 때 초기화될 수 있어 관리자 터미널에서 `setx /M`으로 시스템 변수에 등록한다. 시스템 변수는 같은 PC의 다른 사용자도 읽을 수 있다는 점을 함께 알린다. `Set-ExecutionPolicy -Scope Process Bypass`는 현재 PowerShell 창의 실행 정책만 설정한다. setup.ps1을 실행한 뒤에는 터미널 프로그램을 완전히 다시 열어야 바뀐 Path가 반영된다. HSC-AI의 현재 안내 또는 운영 담당자에게 API 주소와 모델 ID를 확인한다.

## 21. 실행 성공과 프로젝트 분석 성공을 따로 확인

샘플 검증이 통과해도 실제 프로젝트의 빌드 환경까지 검증된 것은 아니다. `pi`를 찾지 못하면 새 터미널인지, setup.ps1을 실행했는지부터 확인한다. 오류 메시지를 모델 문제, 서버 문제, 빌드 맥락 문제로 나눠 확인한다. 공백·한글 경로는 자동 검증 시나리오에도 포함한다.

## 22. 설명은 공식 규약과 현재 구현을 기준으로

웹 자료를 열 수 없는 발표 환경에서도 본문 설명은 동작한다. 링크는 근거를 추적하기 위한 것이고 화면 렌더링에 네트워크는 필요 없다. 발표 직전 Windows CI 상태와 사내 API 안내를 확인한다.

## 발표 전 확인

- 15번 슬라이드는 97b5071 Windows CI 성공을 반영했다. 구현이 바뀌면 해당 버전의 CI 상태로 갱신한다.
- 사내 API 안내에 따른 모델 ID와 프로젝트별 SDK·헤더·패키지를 확인한다.
- 데모는 복사한 샘플 프로젝트로 진행한다. 실제 키나 업무 코드를 화면에 노출하지 않는다.
- `←`/`→`, 화면 클릭, 하단 버튼으로 이동하고 `F`로 전체화면, 브라우저 인쇄로 PDF 출력할 수 있다. 출력본은 [setup-slides.pdf](setup-slides.pdf)에 있다. HTML을 고치면 PDF도 다시 만든다.
